## Summary

Added explicit `authentication.jwt.mode: dual`. Bootstrap now accepts exactly `standard`, `legacy`, or `dual`; unknown values continue to fail with `InvalidArgumentException` and a deterministic message. Standard and legacy mode selection remain separate. The dual service implements the existing `JwtTokenServiceInterface`, so the HTTP auth middleware continues to receive one `AuthContext` regardless of token family.

Dual dispatch applies a 16 KiB token limit, requires exactly three non-empty segments, parses an unambiguous flat JOSE header, and validates strict segment encodings before routing. It makes one validator call and never retries a failed token under another profile:

- `typ=winglet+jwt` routes only to `StandardJwtTokenService`, which requires the canonical RS256 profile, trusted `kid`, issuer and canonical claims.
- The historical legacy profile routes only when its header is exactly the two-field `alg=HS256`, `typ=JWT` shape and its signature is 64 lowercase hexadecimal characters. Header and payload must round-trip as standard Base64; `LegacyJwtTokenService` then verifies HMAC and claims.
- Other Base64URL tokens route only to the standard validator to preserve old-standard JWT compatibility. A changed canonical header with an old-standard label still fails signature validation.
- Unknown or malformed encodings fail closed. Header fields must be unique strings from `alg`, `typ`, and `kid`.

The legacy parser now validates its required header, exact Base64 encoding, signature encoding, and input size itself. This keeps its format checks in the selected validator rather than relying solely on the dispatcher.

For auth-based multi-tenant resolution, Core now requires a canonical token with `token_context=tenant` and a validated tenant ID. A legacy token cannot establish tenant scope by adding `token_context`, `tenant_id`, or a configured tenant claim to its payload. Canonical tenant parsing preserves the .NET `tenant_id` and scope. Core's existing `TenantContext` resolver still takes an application-configured tenant code claim; applications must ensure that claim is mapped to the validated canonical tenant ID and must retain their resource-authorization checks.

## Security and compatibility notes

- In dual mode, legacy routing is intentionally limited to the frozen producer format. A producer that changes its header, adds header parameters, switches Base64 conventions, or uses uppercase hex will be rejected and must be assessed before rollout.
- Legacy-only validation now rejects malformed or non-historical headers and inputs over 16 KiB. Confirm deployed legacy producers match the frozen `HS256` / `JWT` header, standard Base64 payload, and lowercase hex HMAC before enabling the mode.
- Auth-based multi-tenancy now rejects legacy and old-standard contexts. Services relying on legacy `tenant_code` claims for auth-based tenant selection must migrate to canonical tenant scope and a trusted tenant-ID-to-code mapping, or use an independently trusted resolver with application resource authorization.
- Standard-only mode retains the existing standard validator behavior. Legacy-only mode remains selected explicitly. Dual mode does not infer privileges from roles; malformed privilege lists produce no grants, and canonical scope is not manufactured for legacy tokens.
- Canonical tenant endpoints must continue to enforce application/.NET resource authorization. This Core change does not replace that authorization decision.

## Integration and release procedure

1. Configure `authentication.jwt.mode: dual` only for services that must accept both issuers during a migration window.
2. Configure the standard issuer and trusted RS256 public key/JWKS for canonical tokens. Inject the legacy HMAC secret through the configured secret provider; do not commit it or bake it into an image.
3. Exercise real actor, service-principal, and legacy producer tokens through the service HTTP pipeline. Confirm 401 for malformed/expired/tampered tokens and expected 403 behavior for insufficient privileges.
4. For auth-based multi-tenancy, supply and validate the application's tenant-code mapping against canonical `tenant_id`, then run tenant resource authorization tests. Legacy tokens must remain rejected for that path.
5. Run the separately gated Docker HTTP integration with the real producers before release; record issuer revisions, image digests, and runtime versions without recording secrets or bearer tokens.
6. Remove dual mode after the legacy migration window, then release through the normal review and deployment process.
